#73 指标体系 中等

GMV 可以按天、按部门 SUM，转化率和库存为什么不行？可加、半可加、不可加指标怎么汇总？

可加指标半可加不可加比率汇总COUNT DISTINCT

🎯 考察意图

考察候选人会不会按可加性决定报表怎么汇总，而不是看见数字就 SUM、看见比率就 AVG。要能分清可加（GMV）、半可加（库存/余额）、不可加（转化率、客单价、DAU、UV），并说出比率必须「先加分子分母再相除」。只会背「别直接平均转化率」、说不清库存为什么不能按天加、去重人数跨切片对不上，这题就浅了。

📐 回答框架

  1. 先给定义：可加=沿任意维 SUM 仍有业务含义；半可加=只沿部分维可加；不可加=SUM/AVG 都会撒谎，要另给汇总规则。
  2. 可加：金额、订单数、PV、成功笔数；跨天、跨部门、跨渠道都能加，是贡献度拆解的底盘。
  3. 半可加：时点快照（库存、余额、在投人数）可沿商品/仓加，不能沿时间加；时间维用期末、均值或独立快照。
  4. 不可加：比率、均值、COUNT DISTINCT、DAU。正确做法是保留原子分子分母，汇总时 ratio-of-sums，或按说明书重算去重。
  5. 收口：指标说明书必须写「可加性 + 汇总函数」；语义层禁止对不可加字段暴露默认 SUM。

💬 参考答案（口述版）

一句话：先问这个数「沿哪个维度相加还有没有意义」。GMV、订单数是可加的，库存是半可加的，转化率、客单价、DAU、UV 是不可加的——报表该 SUM、该取期末、还是先加分子分母再相除，全写在说明书里，不能靠看板默认聚合。

可加（Additive）。 沿任意维度 SUM 都讲得通：GMV、支付成功金额、订单数、PV、曝光次数、退款笔数。月 GMV = 各天 GMV 之和，全国 = 各部门之和。贡献度、对账、OLAP 下钻都依赖这一层。面试补一句：可加不等于「永远加正数」——退款可以是负事实，仍然可加，加完是净额。

半可加（Semi-additive）。 只对部分维度可加。典型是时点快照：库存件数、账户余额、在途订单、在投用户数。沿商品、仓库、账户 SUM 有意义（今天全仓库存 = 各仓之和）；沿日期 SUM 没有意义——把 30 天库存加起来不是「月库存」，是把同一批货数了 30 遍。时间维正确汇总：期末（最后一天）、期初、日均（先按天取快照再平均）。余额类同：不能把每天余额加出「月余额」。

不可加（Non-additive）。 SUM 和简单 AVG 都会错。
1. 比率 / 均值：转化率 = 订单数 / UV，客单价 = GMV / 订单数，CTR = 点击 / 曝光。部门 A 转化 10%、B 转化 2%，不能 (10%+2%)/2 当公司转化——流量大的组权重大。正确是 ratio of sums：SUM(订单)/SUM(UV)，不是 AVG(各组转化率)。加权平均可以，权重必须是分母。
2. COUNT DISTINCT / UV / DAU：人在渠道 A 和渠道 B 都出现过，部门 SUM(UV) 会重复计数，加总 > 公司 UV。跨天 SUM(DAU) 更不是 MAU。要公司级去重，必须回到原子明细或 bitmap/HLL 按说明书重算，不能加汇总表。
3. 分位数、留存率、渗透率：P90 不可加；留存是队列比率，不能把各天留存加起来。

SQL 里原子层要留分子分母，禁止过早写成一个百分比列让下游乱 SUM：

-- 原子（可加）
SELECT dt, channel, SUM(gmv) AS gmv, COUNT(*) AS orders, COUNT(DISTINCT user_id) AS uv
FROM dwd_pay_success
GROUP BY dt, channel;

-- 汇总到天：比率必须重算；UV 不能 SUM
SELECT dt,
       SUM(gmv) AS gmv,
       SUM(orders) AS orders,
       SUM(gmv) / NULLIF(SUM(orders), 0) AS aov,          -- 客单价：ratio of sums
       SUM(orders) * 1.0 / SUM(uv) AS cvr_wrong          -- 错：channel UV 相加有重复
FROM channel_daily
GROUP BY dt;

公司转化、公司 UV 要回明细或用 HyperLogLog/bitmap 按 dt 去重。渠道日报里的 UV 只保证「渠道内去重」，跨渠道不可加，说明书里写「半可加/不可加」，看板别开合计行。

口述例子：销售周报各部门自己算转化率，CEO 把 8 个部门转化率一平均，说公司转化 4.2%；你用全公司订单/全公司 UV 算出 3.1%。差在流量最大的渠道转化低，简单平均给了小部门同等权重。库存周报把 7 天库存 SUM 成「周库存 70 万件」，其实每天大约 10 万，应报期末 10.2 万、日均 9.8 万。

收尾：面试官要听的是「可加 SUM、半可加时点用期末/均值、不可加保留分子分母做 ratio-of-sums，去重人数跨切片要重算」。能主动禁止语义层对比率列默认 SUM，这题就过了。

💭 面试官可能的追问

追问 1：看板已经存了每天的转化率，业务要看「周转化」，AVG 七天可以吗？和加权有什么差别？

几乎都不该 AVG。七天转化率简单平均是「每天同等权重」，周一 UV 10 万、周日 UV 1 万，周日会把周转化拉偏。正确周转化 = 周订单合计 / 周 UV 合计（周 UV 还得按周去重，不是 SUM(DAU)）。若坚持「日转化的平均」必须声明是算术平均、给的是日波动中枢，不是真实转化；加权平均用每天 UV 当权重，结果接近但在去重和跨天重复访问上仍不等于周口径。说明书里「周转化」只保留一种：分子分母按周重算。

追问 2：库存、余额这类半可加事实，模型上怎么存、报表怎么配聚合？

用周期快照事实表，粒度是「日×商品×仓」或「日×账户」，每天一张切片，度量是时点值。查询默认 dt = 期末 或 argMax(qty, dt)；日均库存是先按天取快照再 AVG，仍不要 SUM 日期。物化汇总表可以预计算「仓合计、类目合计」这些可加维，时间维只存期末和日均两列，禁止存「月库存合计」。SCD/拉链表管的是维度历史，不能拿来当库存可加的借口。

追问 3：COUNT DISTINCT 跨渠道对不上，有哪些工程手段？近似去重能当可加指标用吗？

精确：回到原子事件按目标粒度重算；或用 Roaring Bitmap 存每天/每渠道的用户集合，公司级是按位或，不是 SUM。近似：HLL 可 merge，合并后仍是近似基数，误差要写进说明书，低基数渠道别当精确人数。两种都不是「把各渠道 UV 加起来」。预聚合表要同时保留可加原子（订单、GMV、曝光）和可合并的去重结构；只留一个 UV 整数的汇总表，上卷必然错。

⚠️ 常见踩坑

  • 对转化率、CTR、客单价做 SUM 或简单 AVG，不按分母加权也不回原子层重算
  • 把每天 DAU 加总当 MAU，或把各渠道 UV 加总当公司 UV
  • 库存、余额沿日期 SUM，把时点快照当成期间发生额
  • ADS 过早只留一个百分比列，下游除了乱聚合没有分子分母
  • 语义层/OLAP 对所有数值列默认 SUM，不可加指标没有单独的聚合规则
  • 贡献度拆解拿不可加指标直接当因子相加，加总对不上总差额还四舍五入糊弄

🧠 记忆锚点

可加才能 SUM，半可加时点用期末或日均，比率先加分子分母再相除，去重人数跨切片必须重算。
