#72 数仓建模 中等

什么是一致性维度和总线矩阵？跨数据域复用维度时怎么保证口径不漂？

一致性维度总线矩阵维度复用数据域代理键

🎯 考察意图

考察候选人会不会把「用户、商品、渠道」做成全仓共用的一张真相维，而不是每个主题各写各的 dim_user。只会背星型模型、说不清总线矩阵怎么画、自然键对不上、SCD 策略各域各搞，跨域 GMV 和用户数对不齐，这题就浅了。

📐 回答框架

  1. 先给定义：一致性维度是跨事实表、跨数据域共用同一套键、粒度和属性口径的维度；总线矩阵是「过程 × 维度」的复用清单。
  2. 说清为什么要有：没有它，交易、流量、客服三张事实表的「用户」对不上，看板永远三个数。
  3. 落地三件套：统一代理键与自然键、属性主人与 SCD 策略、变更广播到下游宽表。
  4. 总线矩阵怎么用：先列业务过程，再打钩公共维，禁止每个域私自加同义维。
  5. 收口：一致性是契约，不是「大家从表里 select 同一个字段名」。

💬 参考答案（口述版）

一句话：一致性维度（Conformed Dimension）就是全仓共用的那张「用户 / 商品 / 渠道 / 日期」——键一样、粒度一样、属性口径一样。总线矩阵（Bus Matrix）是一张表：行是业务过程（下单、支付、曝光、退款），列是公共维度，打钩表示这个过程必须用这张维，不许再造一套。

先把反例说出来。 交易域 dim_user 用注册账号、粒度到账号；流量域 dim_uid 用设备，粒度到 device_id；会员域又按手机号去重。三个看板的「用户数」「新客 GMV」对不上，不是 SQL 写错，是维没对齐。面试官要听的是：星型模型解决的是单主题好查，一致性维度解决的是跨主题能拼。

一致性的最低标准，口述四条就够。
1. 同一自然键、同一代理键。 用户的业务主键（如 user_id）全仓唯一；代理键 user_sk 由维表统一发放，事实表只挂 sk，不在事实里重新 hash 一套。自然键变更（账号合并、手机号换绑）走维表映射，不要让每个事实表自己写 coalesce。
2. 同一粒度。 「用户」到底是账号、人、还是设备，必须写进维说明书。账号≠人：一人多账号要有桥接表或黄金 ID，不能假装 COUNT DISTINCT user_id 就是人数。
3. 同一属性口径。 channel 是投放渠道还是首次归因渠道？is_new 是当日新注册还是当日首单？属性只能有一个主人（通常是维表或语义层），事实表禁止各写各的 case when。
4. 同一 SCD 策略。 渠道改名、商品类目调整，Type 1 覆盖还是 Type 2 拉历史，全仓一策。交易用 Type 2 保留下单时类目、流量用 Type 1 只留当前类目，同比就会漂。

总线矩阵怎么画、怎么用。 先列业务过程（不是先列部门）：下单、支付、履约、退款、曝光、点击、客服会话。再列公共维：日期、用户、商品、门店、渠道、券。过程与维的交叉打钩——支付必须挂用户、商品、渠道、日期；曝光可以没有订单但必须有用户/设备、内容、渠道。新需求先改矩阵：缺维就补公共维，而不是在 ADS 里 inflat 一个 user_type2。矩阵也是分工图：维表由平台或主数据负责，事实表由各域负责，谁改属性谁发变更通知。

落地时三张表要能讲出来。
- dim_user：user_sk + 自然键 + 稳定属性 + 生效区间（若 Type 2）。
- map_user_id：账号合并、设备登录、注销后的身份映射，供事实表对齐。
- 事实表：只存 sk + 退化维（订单号这类）+ 度量；描述性属性全部 join 维表，或从维表物化进 DWS，但公式主人仍在维。
日期维几乎总是一致性维：自然日、财年、节假日、是否工作日，同比用同一张 dim_date，不要每个域自己 dayofweek()。

口述例子：电商要「新客首单 GMV」和「投放新客成本」对得上。用户维统一 user_sk，first_order_date 只在用户维算一次（支付成功且非 0 元单，口径写说明书）。交易事实、投放事实都 join 这张维，用 dt = first_order_date 切片。渠道维也必须共用：投放侧的 campaign 映射到交易侧的下单渠道，用同一份渠道树，禁止投放叫「头条」、交易叫「字节-信息流」却没有映射表。

收尾：面试官要听的是「一致性 = 键 + 粒度 + 属性 + SCD 四对齐 → 总线矩阵管复用 → 维表有主人、事实只挂 sk」。能主动说账号≠人、属性禁止事实表私自 case when，这题就过了。

💭 面试官可能的追问

追问 1：两个域的「用户」对不齐，一个是账号一个是设备，总线矩阵要怎么改？一定要合成一张维吗？

不一定合成一张物理表，但必须有可声明的关系。正确做法是：账号维、设备维都是一致性维，再用桥接表 br_user_device（含生效区间）描述登录关系；总线矩阵上曝光过程钩设备，支付过程钩账号，需要「人」口径时走黄金 ID 或桥接，不要把 device_id 硬塞进支付事实冒充用户。合成一张宽维（所有 ID 拍平）会把粒度和 SCD 搞脏，只适合 ADS 加速，不适合当主数据。

追问 2：商品类目调整了，历史 GMV 按新品类还是按下单时类目？和一致性维度怎么配合？

这是 SCD 策略问题，必须全仓统一或按分析用途显式提供两列。类目树常 Type 2：维表保留 category_sk 历史行，事实表存下单时的 category_sk，报表默认「下单时类目」；若业务要「按当前类目重述」，用当前有效行的自然键回滚关联，并在说明书写「重述口径」。最怕交易 Type 2、流量 Type 1，两边都叫一致性维其实策略不一致。

追问 3：已经有很多各域私有 dim_xxx，怎么收敛成总线，而不停数仓重做？

先盘点高频交叉：用户、商品、渠道、日期、组织，列为公共维，冻结自然键和属性主人。各域旧表改成视图或映射层指向公共维，事实表逐步把自然键换成公共 sk，允许一个过渡期双写。新过程强制过总线矩阵评审：没有打钩不准上线同义维。不要一上来合并所有属性——先对齐键能 join，再收口易漂的属性（新老客、渠道、类目）。

⚠️ 常见踩坑

  • 把字段名相同当成一致性，账号 id 和设备 id 都叫 user_id 就直接 join
  • 每个数据域各自发代理键，跨域事实表 sk 对不上
  • 属性口径写在事实表 case when 里，维表只是摆设
  • SCD 策略各域各搞，历史重述和「当时类目」混用还不声明
  • 总线矩阵按组织架构画而不是按业务过程画，维复用变成部门墙
  • 日期、时区、财年各自 dayofweek()，同比对不齐还以为是 SQL 问题

🧠 记忆锚点

一致性维度是跨域共用的键、粒度和属性口径；总线矩阵管谁必须挂这些维，维表有主人，事实只挂代理键。
