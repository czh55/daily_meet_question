#81 数据质量 中等

事实表关联维表对不上，你怎么处理？未知成员、孤儿事实、参照完整性怎么做？

参照完整性未知成员孤儿事实迟到维代理键

🎯 考察意图

考察候选人会不会把「JOIN 不上」当成参照完整性事故，而不是一句 LEFT JOIN。说不清孤儿事实、未知成员、迟到维和代理键占位，或用 INNER JOIN 把对不上的订单从 GMV 里吞掉，这题就浅了。

📐 回答框架

  1. 先定性丢键原因：源就缺维、抽取漏了、键对不齐（类型/空格/大小写）、还是维比事实晚到。
  2. 模型侧：事实只挂代理键；维表预置未知成员（如 sk=-1）；禁止用 INNER JOIN 把金额吞掉。
  3. 质量侧：参照完整性进门禁，输出孤儿样本键，而不是只报「有几行对不上」。
  4. 迟到维：先挂未知成员让事实落地，维到了再按业务键回刷代理键。
  5. 收口：根因修源系统或补维抽取，报表层 silently 过滤不算治理。

💬 参考答案（口述版）

一句话：事实对不上维，先当参照完整性事故，不要先改 SQL 把行滤掉。维表预置未知成员，事实先挂上让金额在；门禁把孤儿键打出来；维迟到了再回刷代理键。INNER JOIN 维表把 GMV 吞掉，是事故不是技巧。

先给现象命名。 事实表有 order_id、有金额，但 sku_key / user_key 在维表里找不到对应行——这叫孤儿事实（orphan fact）。不是「LEFT JOIN 就能交差」：LEFT JOIN 只是不丢行，不解释键为什么丢、钱算在哪个类目下。

丢键常见四类，面试先分型再动手：
1. 源就缺：下单时 SKU 已下架、用户未落会员表、测试单没维。要源系统补，不是数仓编一个真维。
2. 抽取漏：维是全量漏增量、软删被滤、CDC 位点落后。维表比事实旧。
3. 键对不齐：sku_id 一边是 ' 1001'、一边是 1001；string vs bigint；大小写；末尾换行。对账看起来「有这个货」，JOIN 对不上。
4. 迟到维（late-arriving dimension）：事实先到（订单已支付），维后到（商品主数据隔日同步）。合法，但不能让这笔 GMV 从日报消失。

模型怎么接。 星型里事实表只存代理键（surrogate key），不拿业务键满世界 JOIN 当前维。维表第一天就插入未知成员：

-- 维表预置，禁止业务用这个 id
INSERT INTO dim_sku (sku_sk, sku_id, sku_name, cate_name, is_unknown)
VALUES (-1, '_UNKNOWN', '未知商品', '未知类目', 1);

事实装载时 LOOKUP 维：命中用真 sk，未命中写 -1，事实行照样插入。看板用 LEFT JOIN 也能出数，未知类目单独一列，金额在，不在「少了 3% 还当对账过」。

装载伪代码：

INSERT INTO fct_pay_d (dt, order_id, sku_sk, pay_amt)
SELECT
  o.dt,
  o.order_id,
  COALESCE(d.sku_sk, -1) AS sku_sk,  -- 对不上挂未知，不丢单
  o.pay_amt
FROM dwd_order_pay o
LEFT JOIN dim_sku d
  ON o.sku_id = d.sku_id
 AND d.is_current = 1;   -- 当天装载用当前版本；历史重述另走 as-of

高压线：不要 INNER JOIN dim_sku。对不上的订单会从事实表蒸发，GMV、订单数、对账同时变少，还没有孤儿样本。

质量门禁查什么。 参照完整性是硬规则，不是「报表 JOIN 一下」。每天对正式分区：

-- 孤儿：事实代理键不在维表，或仍停在未知成员超出宽限
SELECT f.order_id, f.sku_sk, f.pay_amt, f.dt
FROM fct_pay_d f
LEFT JOIN dim_sku d ON f.sku_sk = d.sku_sk
WHERE f.dt = DATE '2026-11-21'
  AND (d.sku_sk IS NULL OR d.is_unknown = 1);

规则分层可以和门禁那题对齐：未知成员占比超阈值（如金额 >0.5%）→ 告警；完全找不到 sk（连 -1 都没有，说明 LOOKUP 写崩了）→ 阻断。输出必须带样本键，方便补维。只报「孤儿 1200 行」补不了数。

迟到维怎么收口。 当天维没到：事实挂 -1，日报 GMV 完整，类目切到「未知」。维到了（次日或小时级补抽）：
1. 用业务键再 LOOKUP，得到真 sku_sk；
2. 按 order_id（或事实主键）UPDATE / MERGE 回刷代理键，只改 sk，不改金额、不改 dt；
3. 重跑依赖类目的 DWS，重跑门禁。
不要等维到了再装事实——支付 GMV 的 SLA 通常比商品主数据紧。也不要在事实里长期留业务键当「反正能 JOIN」：SCD2 一开新链，业务键会挂到当前版本，把昨天订单改成今天的类目。

和相邻概念划界。
- 未知成员 ≠ 垃圾维：垃圾维是把低基数标志（是否新客、是否券后）合成一维；未知成员是「这条事实暂时/永远对不上维」。
- 未知成员 ≠ 桥接表：多对多用桥接（优惠券那题）；一对多对不上用未知成员。
- 参照完整性 ≠ 源仓对账：对账比的是源和仓是不是同一批键；参照完整性比的是事实键在不在维里。两边都过，数才既全又挂得上属性。

收尾：面试官要听的是「分型 → 未知成员占位 → 门禁打孤儿样本 → 迟到再回刷 sk」。能主动说禁止 INNER JOIN 吞 GMV、回刷只改代理键不改金额，这题就过了。

💭 面试官可能的追问

追问 1：事实今天到、维明天才到，未知成员要挂多久？回刷代理键会不会把历史类目改掉？

SLA 内（例如 T+1 主数据完成前）挂未知是预期，门禁用 warning 而不是 blocker。超过宽限仍是 -1，升级为阻断或事故：多半抽取漏或源就没有这条 SKU。回刷只改 sku_sk，金额、支付日、订单号不动；DWS 按事实 dt 重跑类目汇总，所以「昨天那笔订单的类目」会从未知变成真类目——这是补全，要声明看板 as_of。禁止顺手用今天的 SCD2 当前行去改更早的事实：历史订单应按下单/支付日 as-of 对应当时维版本，否则类目重述和迟到补键会混成一锅。

追问 2：未知成员要不要拆成「未匹配 / 已删除 / 测试」几个？和垃圾维怎么分工？

核心金额表建议至少拆未匹配（迟到或键对不齐）和无效（测试、已删除、明确无维）。未匹配要回刷，无效不应回刷成真品类，否则测试单会进经营类目。代理键可以 -1/-2/-3，或一个未知行加 unknown_reason。不要把「是否未知」塞进垃圾维当普通标志——垃圾维是合法低基数属性的笛卡尔，未知是参照失败。报表要把未知类目单列，禁止把 -1 的金额摊进「其他」里藏掉。

追问 3：维表做了 SCD2，事实当时挂的是旧代理键，后来开了新链，孤儿检查会不会误报？装载该用当前行还是 as-of？

孤儿检查必须按代理键存在性，不要按「业务键是否等于当前行」。旧 sk 仍在维表（只是 is_current=0），参照完整性通过，这不是孤儿。误报常见于检查写成 JOIN dim ON biz_key AND is_current=1，把历史 sk 判死。当天增量装载：对「事件发生时」as-of 查找当时有效的维版本（start_dt <= event_dt < end_dt）；对迟到补键，也用事实事件日 as-of，不要一律挂最新当前行。拉链/SCD 那题的半开闭约定在这里同样有效。

⚠️ 常见踩坑

  • INNER JOIN 维表，孤儿订单从 GMV 消失还当对账通过
  • 没有未知成员，代理键 NULL，GROUP BY 类目时金额进了无名桶或被引擎丢掉
  • 用业务键直接 JOIN 维表当前行，SCD2 一开新链就把历史订单改挂到今天属性
  • 把孤儿当脏数据 DELETE，其实是维抽取延迟，钱被删了补不回来
  • 参照完整性只 COUNT 对不上的行，不留 order_id/sku_id 样本，无法补维
  • 维表物理删除下架商品，历史事实全部变成孤儿
  • 迟到回刷用今天的当前维版本，而不是按下单/支付日 as-of

🧠 记忆锚点

事实对不上维先挂未知成员，禁止 INNER JOIN 把钱吞掉；孤儿是质量事故，维到了再按事件日回刷代理键。
