#68 数据质量 中等

上游加了字段、改了类型，下游作业挂了。数据契约和 Schema 演进你会怎么做？

数据契约Schema 演进向后兼容破坏性变更Schema Registry

🎯 考察意图

考察候选人会不会把「下游炸了」拆成契约缺失和兼容性判断，而不是只会回滚上游。要能说清兼容变更（加可选字段、给默认值）和破坏性变更（改类型、改语义、删字段）的发版路径，以及契约必须进 CI / Schema Registry，不能停在 wiki。只背 Data Mesh / Contract 名词、说不清消费者怎么升级和回滚，这题就浅了。

📐 回答框架

  1. 先验事故类型：加字段、改类型/空值、删改名，还是字段名没变但语义变了。
  2. 契约写什么：字段、类型、空值、主键、兼容级别、主人、SLA，而且要可执行。
  3. 兼容变更：加带默认值的可选字段；禁止 SELECT * 和按位置反序列化。
  4. 破坏性变更：双字段或双版本过渡，消费者先升级再切，保留回滚点。
  5. 收口：注册中心或表契约挡发版；群通知不算发版。

💬 参考答案（口述版）

一句话：下游炸了，先判断这是兼容变更没声明，还是破坏性变更没走过渡。数据契约是生产者对消费者的可执行承诺，不是一篇 wiki；Schema 演进的关键是「旧消费者能不能读新数据、新消费者能不能读旧数据」。

先给事故分型，别一上来改回滚。
1. 加字段：JSON 下游可能无感，但 Avro/按位置的 Protobuf、以及 SELECT * 写进下游表，会错位或类型对不上。
2. 改类型：string 改 int、精度变小、时间戳从秒改毫秒，旧数据和新作业对不上。
3. 改空值约束：可选变必填，历史 NULL 直接让作业失败。
4. 最毒的一种：字段名没变、语义变了。例如 status=1 从「成功」变成「处理中」。对账和对实验都会 silently 错。

契约至少写七件事，写不出就不要叫契约。
① 字段名与类型；② 是否可空、默认值；③ 主键 / 业务唯一键；④ 枚举值与状态机；⑤ 兼容性承诺（向后 / 向前 / 双向）；⑥ 主人（谁能改）和消费者名单；⑦ 新鲜度 / 完整性 SLA。表、Topic、接口都适用。口述形状：

order_paid_v1
  order_id   string  NOT NULL  PK
  pay_amt    decimal(18,2) NOT NULL
  pay_status enum{success,refunded} 
  pay_time   timestamp 业务时区
  兼容：向后兼容（可加带默认值字段）
  主人：交易数据组

没有消费者名单，改完才发现有人 SELECT *，这叫事故，不叫演进。

兼容变更可以热发，但有条件。
- 加字段：给默认值或声明可选。新消费者用得上，旧消费者忽略。
- 加枚举：旧消费者必须有 unknown 分支，否则新值当非法。
- 类型放宽（int→bigint）多数可读，类型收窄（bigint→int）当破坏性。
- 禁止：改名当「整理」、调换列顺序、让下游靠位置解析。Hive/Spark 动态分区 + SELECT * 是重灾区，下游表结构要显式列清单。

向后兼容：新 Schema 能读旧数据（旧行没有新列就填默认值）。向前兼容：旧 Schema 能读新数据（多出来的字段可跳过）。流式场景两边都要，才叫 FULL。只说「加列一定兼容」是错的，取决于序列化是按名字还是按位置。

破坏性变更必须走过渡，不能靠群里说一声。
典型路径：
1. 双字段：新增 pay_amt_fen，旧 pay_amt 继续写；下游先双读校验，再切新列，最后下线旧列。
2. 双版本：Topic order_paid_v2 或表分区带 schema 版本；消费者按版本分发。
3. 顺序：先扩消费者（能读新旧）→ 再扩生产者 → 观察一个完整业务周期 → 再删旧。反了就会有一段时间无人能读。
4. 回滚点：新旧并行期内保留旧字段；切完至少留一个可回刷窗口。

契约要挡发版，不要挡事故。 生产者 CI：Schema 相对上一版做兼容性检查（Registry 的 TRANSITIVE 模式最省心）。消费者 CI：用契约生成的样例 fixture 跑作业，上游改了没通知会红。表侧可用 dbt contract / 建表 DDL 校验。线上再加一条：未知字段、未知枚举、空主键，进死信或质量表，而不是让整作业挂掉。

口述案例：支付 Topic 把 pay_amt 从元（decimal）改成分（bigint），消费数仓的金额乘了 100，对账第二天炸。正确做法是发 pay_amt_fen，契约声明旧字段 deprecated 两个迭代；下游双读对账，误差为 0 再切；Registry 拒绝「同字段改类型」的兼容检查。群里发「今晚改类型」不算发版。

收尾：面试官要听的是「先分型 → 契约七要素 → 兼容靠默认值和按名解析 → 破坏性靠双字段/双版本 → CI 挡发版」。能主动说语义变更比改类型更危险，这题就过了。

💭 面试官可能的追问

追问 1：没有 Schema Registry，只有 JSON 日志和 Hive 表，你怎么先落地契约？

先把核心表/Topic 的字段清单收成一份 YAML 或 dbt schema，主键、可空、枚举写进去，生产者发版 MR 必须 diff 这份文件。Hive 表禁止 SELECT * 建下游，写入用显式列。JSON 侧在解析时按名字取字段、未知字段进 _extra，必填缺失打质量表而不是让 Spark 直接 fail。Registry 可以后补；先有可审查的 diff 和消费者名单，比先上 Confluent 更要紧。

追问 2：已经把破坏性变更发到生产了，下游大面积失败，你怎么止血？

先停生产者新版本或把流量切回旧 Schema，不要在错误数据上继续「修作业」。用 Registry / 分区版本定位从哪个偏移或哪个 dt 开始坏。能回放就按旧契约重放；不能回放就对已落地分区做补偿：双字段补齐、错误类型行进隔离表。对外 SLA：核心报表降级到上一稳定分区，并公告「从某时点到某时点数据不可用」。事后把这次变更类型加进兼容性检查的拒绝规则，避免同一错误再发一次。

追问 3：一张 200 列的宽表，契约怎么维护才不会变成摆设？

不要一张表一个巨型契约。按消费切成稳定内核（主键、金额、状态、时间）和可演化扩展（属性、标签）。内核变更走破坏性流程；扩展列允许加可选字段。宽表本身就该怀疑：能拆主题域就拆，契约按主题域签。每个字段必须有主人，没主人的列不允许进认证层。定期用血缘看哪些列 90 天无读取，先标记 deprecated 再删。契约评审看「谁在读」，不看「列多不多」。

⚠️ 常见踩坑

  • 认为加字段一定兼容，忽略 SELECT *、按位置反序列化和动态分区错位
  • 字段名不变只改语义，对账和实验都 silent 错
  • 契约写在 wiki，CI 不挡，生产才发现消费者还在
  • 破坏性变更只发群通知，没有双字段过渡和回滚点

🧠 记忆锚点

契约是可执行承诺不是 wiki：兼容变更靠按名解析和默认值，破坏性变更靠双字段或双版本，CI 挡发版。
