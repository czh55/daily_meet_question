#67 指标体系 中等

同一指标三个看板三个数，你怎么治理口径？语义层 / 指标平台解决什么问题？

语义层指标平台口径治理权威数据源指标说明书

🎯 考察意图

考察候选人会不会把「三个看板三个数」拆成口径分叉，而不是先怪数仓错了。要能说清指标说明书、权威表、语义层各管什么，以及平台解决不了质量事故和错误源表。只背 LookML / 指标中台名词、说不清主体去重键和变更双跑，这题就浅了。

📐 回答框架

  1. 先验真再定罪：是数据错了、取数窗口不同，还是同一名字三套口径。
  2. 把指标写成说明书：主体、时间窗、成功态、去重键、含不含退款/税、权威表。
  3. 语义层做什么：度量定义一次、维度可切片、消费端只引用不复制 SQL。
  4. 治理：主人、变更评审、新旧双跑、下线散落 SQL；平台不是自动正确。
  5. 收口：口径唯一靠契约，不靠口头对齐；看板只是语义层的一种消费。

💬 参考答案（口述版）

一句话：三个数通常不是「仓错了」，而是同一中文名背后三套分子分母。先对齐说明书，再谈语义层把定义收成一份；平台解决的是复制粘贴，不是数据质量。

先拆三种「对不齐」，别一上来改表。
1. 假分歧：窗口不同（今日 10 点对昨天全天）、时区、是否含当天未完成分区。对账应对齐同一快照。
2. 真口径分叉：成功态不同（下单 vs 支付 vs 剔除退款）、去重键不同（订单 vs 买家）、主体不同（登录用户 vs 设备）。名字都叫 GMV，公式不是一个。
3. 源表分叉：有人扫 ADS 宽表，有人从 DWD 现算，过滤条件各写各的。仓可能都对，消费各算各的。

指标必须能写成说明书，写不出就不要上看板。 最少六项：① 主体（谁，买家还是订单）；② 时间窗与时区（下单日还是支付日，业务时区）；③ 成功态（哪些状态计入）；④ 去重键；⑤ 含不含税、运费、退款、刷单；⑥ 权威表与主人。口述例子：

GMV_支付成功_未退 =
  SUM(pay_amt) WHERE pay_status='success'
  AND refund_amt=0
  时间键 = pay_time 的业务日
  权威表 = dws_trade_pay_daily

看板标题写中文名不够，要能点到这份定义。

语义层解决的是「定义只写一次」。 消费端（看板、取数、实验、逆向分析）引用度量名和维度，不再每人复制一段 SUM CASE。它通常长这样：度量 = 聚合表达式 + 过滤器；维度 = 可切片属性；查询时由引擎拼 SQL 或读预聚合。LookML、dbt metric、Headless BI、公司里的指标中台，都是这个形状。好处三条就够：改口径改一处；同一 GMV 切渠道/新老不会各写各的成功态；权限和认证可以挂在度量上，而不是挂在某张临时表。

它不自动让数变对。 上游空跑、埋点丢事件、分区延迟，语义层照样吐错数。权威表仍要质量规则和对账；语义层只保证「大家读的是同一公式」。也别把语义层做成「超级宽表」：度量膨胀、没有主人，会变成第二个口径坟场。

治理动作要能落地。 ① 每个核心指标有 R 主人（口径）和 A 拍板（业务）；② 变更走评审：新旧定义双跑至少一个完整周期，公告生效日，历史对比标明断点；③ 散落 SQL 限期切到引用，过期看板下线；④ 取数门户默认搜度量名，而不是开放「从 ODS 自己写」。面试加分：提到「认证指标」和「探索指标」分层，认证的才能进 OKR 和实验主指标。

口述案例：增长看板 GMV 1.2 亿、财务 1.05 亿、数据组 1.11 亿。对齐后发现增长用下单未支付、财务用开票含税、数据组用支付成功未剔当周退款。收口到 dws_trade_pay_daily 的支付成功且 7 日未退，语义层挂 gmv_paid_net，三个看板改引用。下个月财务改含税规则，只改度量并双跑，不再口头通知三个分析师。

收尾：面试官要听的是「先分清真假分歧 → 说明书六要素 → 语义层收复制 SQL → 主人与双跑」。能主动说平台治不了空跑和错源表，这题就过了。

🔍 关键词

语义层指标说明书权威表成功态认证指标口径双跑

💭 面试官可能的追问

追问 1：没有指标平台，只有数仓和一堆 SQL，你怎么先止血？

先冻结核心指标名单（10 个以内），每张写一页说明书并指定权威表；看板标题改成带版本的度量名。取数群里禁止直接贴「最终 SQL」，只允许贴权威表 + 过滤条件。散落 SQL 用血缘或仓库搜索（SUM pay_amt、GMV）拉清单，按流量下线或改引用。平台可以后补，契约要先有；否则上了中台也只是把分叉 SQL 搬进 YAML。

追问 2：语义层和 DWS 预聚合表是什么关系？会不会重复？

DWS 解决的是算得快、扫得少；语义层解决的是定义唯一、消费一致。常见落地：高频切片（渠道日、类目日）落 DWS，语义层的度量指向这些表或对它们再聚合；临时维度组合仍走明细 + 同一套过滤器，避免第二套成功态。重复发生在「宽表已经写死 GMV，语义层又写一遍不同过滤」——这时以说明书为准，表是物化缓存，公式的主人在语义层或指标字典，不在某张 ADS。

追问 3：口径要改（比如 GMV 改成剔退款），历史怎么处理？A/B 和 OKR 怎么办？

禁止静默改。新定义新名字或带版本（gmv_paid_net_v2），与旧度量双跑一个完整经营周期；报表标明「口径变更日」。OKR 和实验主指标锁版本：进行中的实验不中途换分母；新周期再切。回溯历史用新口径重刷权威表，同时保留旧口径快照供审计。只改看板文案不改数，叫口径漂移。

⚠️ 常见踩坑

  • 把三个数直接当数据质量事故，不先对齐成功态、时间键和去重
  • 上了指标中台却继续允许每人从 ODS 复制 SQL，平台只是多了一个入口
  • 语义层堆几百个无主人度量，没有认证/探索分层，变成新的口径坟场
  • 口径变更不双跑、不公告生效日，OKR 和实验中途换分母

🧠 记忆锚点

三个数先对说明书：主体、时间键、成功态、去重、含不含退；语义层让公式只写一次，平台治不了空跑和错源表。
